## 1. Continuous day swipe on the calendar  *(Drew's #1)*

Today, swiping between days is a page flip — the next day appears already loaded. Drew wants
the next day to track the finger and come in off-screen, so the transition is continuous.

**Why it was deferred:** this is a gesture-driven rewrite of the most gesture-sensitive screen
in the app. It needs drag state, velocity handling, rubber-banding at the edges, and mid-swipe
cancellation — and it has to coexist with the hand-rolled drag-to-schedule `DragGesture`, which
exists precisely because the native APIs misbehaved here (see CLAUDE.md macOS gotchas; the same
caution applies on iOS). Nothing is broken today, so it is pure polish.

**Where:** `AtlasMobile/Views/Schedule/` — `DayGridView.swift`, `DayTimelineView.swift`, and
whatever owns day paging.

## 2. All-day events are anchored at UTC midnight  *(highest user impact)*

**This is a real, live, day-off bug affecting the shipped Mac app right now.**

Google all-day events are stored anchored at **UTC midnight**, but every consumer buckets by the
**local** calendar. An all-day event on Aug 29 stores `2026-08-29T00:00:00Z`, which is Aug 28
8 PM in Eastern — so it renders on **Aug 28** on Mac and on **both days** on iOS. Write-back
mirrors the error: the editor saves local midnight and serializes the previous date for anyone
east of UTC.

Worse: **Apple/EventKit all-day events come back at LOCAL midnight and render correctly**, so the
app currently holds two incompatible conventions for the same concept. That also breaks dedup —
the match tolerance is 60 seconds, and an Apple copy vs a Google copy of the same holiday differ
by hours *and* land on different local days, so the fallback never reaches the overlap test and
both copies render.

**Files:** `Atlas/Services/GoogleCalendarService.swift:20-26, 91-95, 106-108` ·
`supabase/functions/google-sync/index.ts:219-222, 231-234` · `_shared/ics.ts:137` ·
consumers `Atlas/Data/AppState.swift:1077`, `AtlasMobile/Views/Schedule/DayGridView.swift:501-504` ·
dedup `AtlasCore/Sources/AtlasCore/CalendarSync.swift:164-172` ·
editors `Atlas/Views/Calendar/EventEditorSheet.swift:236-243`, `CalendarEventDetailView.swift:394-400`

**Do it as one deliberate job:** pick ONE convention, apply it across Google, ICS, both editors
and dedup, write tests that pin it, then a visual pass. Deterministic, so it is cheap and
testable — it just must not be rushed. NOTE: the iOS all-day editor fix shipped in 1.0
deliberately preserves whatever anchor an event already has, so it neither fixes nor worsens this.

## 3. Mac voice capture has all three bugs iOS just fixed

`Atlas/Services/SpeechCaptureService.swift` (202 lines) is a completely separate implementation
from `AtlasMobile/Services/SpeechCapture.swift`. Line 185 still has the original pattern:

```swift
if error != nil || (result?.isFinal ?? false) { … }
```

That is "treat final as the user being done" — the first bug fixed on iOS. It also has no
banking/roll logic at all, so the never-final overwrite bug applies too.

**Recommendation: do NOT copy the iOS file across.** It now carries a solution arrived at over
four rounds of debugging; duplicating it guarantees drift. Either rewrite the Mac side
deliberately, or factor the accumulation logic into `AtlasCore` so both platforms share one
tested implementation. Lower priority than it sounds — most people dictate on a phone, not at a
desk with a keyboard in front of them.

## 4. From the iOS dictation audit — not shipped in 1.0

Ranked by the audit; the four highest were fixed for 1.0, these remain.

- **Audio interruptions are not handled at all.** No observer for
  `AVAudioSession.interruptionNotification`, `routeChangeNotification`, or
  `AVAudioEngineConfigurationChange`. A phone call, a Siri invocation, or unplugging headphones
  mid-capture stops the engine but leaves `state == .listening` — the dot keeps pulsing, the
  waveform freezes, and the user talks into nothing until the 60s cap auto-submits a partial.
- **Bluetooth mics are not enabled.** `setCategory(.record, mode: .measurement, options: .duckOthers)`
  lacks `.allowBluetooth`, so AirPods users are recorded by the handset mic. Tradeoff to confirm:
  enabling HFP drops any music on that headset to call quality.
- **Level updates spawn a `Task` per audio buffer** (~47/s) — allocation on the realtime audio
  thread plus main-actor churn re-rendering the whole capture view. Throttle to ~10 Hz.
- **Spoken words are never mirrored to the draft store**, so a crash mid-dictation loses them.
  Typed text has this guarantee; dictation does not.
- **Unsupported locale = permanent "Voice unavailable"** with no fallback to `en_US`.
- **The mic deep link starts dictation regardless of phase** — `atlas://capture?mic=1` arriving
  during `.thinking`/`.result` blows away the result card. Guard on `phase == .empty`.
- **After granting permission in Settings, the user must back out and re-tap** — nothing
  re-checks authorization on return.
- **Ducking blip at the start of every dictation** — `endEngine()` runs before the session is
  configured, firing `setActive(false, .notifyOthersOnDeactivation)` on an inactive session.

## 5. ICS: Outlook-style TZIDs are read as UTC

`supabase/functions/_shared/ics.ts:142-148` — Windows/Outlook zone names
(`Eastern Standard Time`, `(UTC-05:00) Eastern Time…`) throw in `Intl`, fall through, and the
wall clock is then read as **UTC** — a 4-5 hour shift that can roll the date. Affects
Exchange-published registrar feeds, which is exactly the "my school publishes a calendar link"
path the App Store description promises.

Also: floating times resolve to **UTC** server-side but to **local** in
`AtlasCore/Sources/AtlasCore/ICSFile.swift:383-395` — the two parsers disagree on the same file.
`ics_test.ts` has 4 tests and **zero** timezone coverage. No `RRULE` support either, so
recurring feed events yield only the first instance (separate gap, not a shift).

## 6. Smaller / cosmetic

- `AtlasCore/.../CaptureDateParser.swift:6-18` drops zone-less `"2026-06-30T14:00"` → nil → an
  event silently degrades to an undated task. `SyllabusDraft.date` handles that shape; the two
  parsers have drifted. Low impact only because the server always emits absolute instants.
- Capture all-day end is **inclusive**; Google's and ICS's are **exclusive**. Multi-day all-day
  captures also collapse to one day.
- The **class widget deep-links to Today**, not the class hub — needs a new `atlas://class?id=`
  route plus routing in `RootTabView` and the School views.
- Once the 20,000-char capture cap is hit, the user keeps talking with no indication; the typed
  path has "That's as much as one capture can hold" messaging, the spoken path does not.
- `SchoolCalendar.swift:152-157` — zero-length key dates are invisible in the iOS all-day row.

## 7. Watch item, not yet a bug

Bare weekday resolution ("due friday") landed on the FOLLOWING week's Friday twice during the
2026-08-26 session, then resolved correctly 5/5 after the date-anchor calendar was added to the
capture prompt. Currently consistent. If a user reports a deadline landing a week out, this is
the first place to look — the anchor calendar is in `capture/index.ts` (`dateAnchorBlock`).

## 8. iPad support

Deferred from 1.0 deliberately (2026-08-26). `TARGETED_DEVICE_FAMILY: "1"` — iPhone only.
Shipping a stretched phone UI to an iPad reviewer was the risk; the layouts have never been
tested at that size. Revisit when there is time to actually design and test the wider layouts,
not as a checkbox flip.
