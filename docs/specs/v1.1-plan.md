## Phase 1 — All-day and timezone correctness  ⚠️ highest risk, do first and alone

**The bug (live in the shipped Mac app today):** all-day events land on the wrong day.
An all-day event on Aug 29 renders on **Aug 28** on Mac and on **both days** on iOS, and
Apple and Google copies of the same holiday both render instead of deduping.

### The rule we are implementing

> **Timed events are absolute instants. All-day events are floating dates.**

- A 3pm meeting is a moment in time. Fly from New York to LA and it correctly shows at 12pm.
  Timed events render in `Calendar.current` — travel-correct with no special handling.
- "Labor Day, Sept 7" is **not** a moment in time. It must read Sept 7 in Tokyo, in London,
  on a plane, forever. It must never shift.

### How that is encoded (no schema change)

`events.start_at` / `end_at` are `timestamptz` and there is already an `is_all_day` bool
(`supabase/migrations/0001_init.sql:70-81`). We keep that schema and adopt:

**Canonical all-day encoding = UTC midnight of the intended calendar date.**
`2026-09-07T00:00:00Z` means "Sept 7", full stop.

This was chosen over local-midnight because:
- Three of four ingest paths already write it (Google client, Google server, ICS).
- It is already locked by tests (`ics_test.ts:29-31`, `GoogleCalendarMapperTests.swift:52-55`).
- **A server-side job has no user timezone.** `google-sync` runs while the app is closed and
  hardcodes UTC; it has no way to know the user's local day. A UTC-anchored date needs none.
  This is the deciding argument — local-midnight would force a new user-timezone column and
  make the server sync depend on it.

**The corollary that actually fixes the bug:** every consumer of an all-day event must bucket
it with a **UTC calendar**, not `Calendar.current`. Today they all use `Calendar.current`,
which is why a UTC-midnight instant reads as the previous day anywhere west of Greenwich.

### Work

1. **Normalize EventKit at ingest (the one outlier).** EventKit returns all-day events at
   *local* midnight. Convert to UTC midnight of the same calendar date at the boundary, so
   nothing downstream sees two conventions.
   - `Atlas/Services/EventKitService.swift:146-153` (read), `:229-232` (mirror-out — convert back)
   - `AtlasMobile/Services/MobileEventKitService.swift:46`
2. **Fix the editors.** They currently save all-day at *local* midnight, so Atlas-native
   all-day rows are written under the wrong convention.
   - `Atlas/Views/Calendar/EventEditorSheet.swift:236-243`
   - `Atlas/Views/Calendar/CalendarEventDetailView.swift:394-400`
3. **Make consumers read all-day in UTC.**
   - `Atlas/Data/AppState.swift:1075-1088`
   - `AtlasMobile/Views/Schedule/DayGridView.swift:79-81, 466, 558-561`
   - `AtlasMobile/Views/Schedule/MonthPageView.swift:148-149`, `DayTimelineView.swift:201`
   - `AtlasMobile/.../WidgetSnapshotWriter.swift:38-45`
   - `AtlasCore/.../Models.swift:395-399` — `hasSpecificTime` asks `Calendar.current` for
     hour/minute != 0, which reinterprets a UTC instant locally. Must respect `isAllDay`.
4. **Fix dedup.** `AtlasCore/.../CalendarSync.swift:164-172` (`timesMatch`) never consults
   `isAllDay`. Two all-day copies of the same holiday differ by the tz offset and fail both
   the 60s tolerance and the same-day check. All-day events should match on **calendar date**,
   not instant proximity.
5. **Migration for existing rows.** Google/ICS rows in prod are already UTC-midnight and are
   fine. Apple events never reach the DB. **Only Atlas-native all-day rows written by the
   editors are wrong** — a small, targeted migration. Query prod first to size it
   (see [[atlas-live-db-access]] for CLI + PostgREST access); do not run a blind UPDATE.
6. **UI: all-day events get a top row.** They must not paint the entire day column. iOS
   already has an all-day row (`DayGridView.swift:79-81`); the Mac day/week views need the
   equivalent treatment.

### Tests to write (there are currently none for this)

- **Run assertions under a non-UTC timezone.** No existing test does. Pin at least one test
  to something like `America/Los_Angeles` — the bug is invisible under UTC.
- An all-day event ingested from Google, ICS, EventKit, and the editor all produce the
  **same** stored instant for the same calendar date.
- An Apple all-day event and a Google all-day event for the same date **dedupe to one**.
- A timed event keeps its instant and renders shifted when the device timezone changes.
- Round-trip: create all-day in the editor → push to Google → pull back → same date.

**Drew's test:** create an all-day event in Google Calendar for a specific date → it shows on
**that exact date, once**, on both Mac and iPhone, in the top row — not the day before, not twice.

## Phase 2 — ICS Outlook TZIDs read as UTC

Windows/Outlook zone names (`Eastern Standard Time`, `(UTC-05:00) Eastern Time…`) throw in
`Intl`, fall through, and the wall clock is then read as **UTC** — a 4–5 hour shift that can
roll the date. This hits Exchange-published registrar feeds, which is exactly the "my school
publishes a calendar link" path the App Store description promises.

- Map Windows zone names → IANA before handing to `Intl`: `supabase/functions/_shared/ics.ts:142-148`
- **Two parsers disagree on floating times:** server resolves to UTC (`ics.ts:147-148`),
  `AtlasCore/.../ICSFile.swift:383-395` resolves to local. Make them agree.
- `ics_test.ts` has 4 tests and **zero** timezone coverage — add it.
- Known separate gap, not in scope: no `RRULE` support, so recurring feed events yield only
  the first instance.

**Drew's test:** add the school Canvas/registrar ICS feed → an assignment with a known due
time shows at that time, not shifted 4–5 hours or on the wrong day.

## Phase 3 — Settings pass (iOS)

One sweep through iOS Settings. All small, all independent of Phases 1–2.

1. **Remove the "add calendar via ICS link" UI.** `AtlasMobile/Views/Settings/SettingsView.swift`
   lines ~52-63 (state), ~662-691 (connect button + help), ~763-790 (`connectICS()`).
   It called the same server-side `feeds-connect` function as Mac, so **no sync path is lost** —
   a feed added on Mac already appears on iOS. Feeds are managed on Mac, viewed on iOS.
2. **Apple Calendar explainer copy.** Apple scopes calendar access **per device** — there is no
   cross-device API, so connecting on Mac does not connect the phone. This is normal and every
   calendar app works this way; it just needs saying. Suggested copy:
   > "Already connected Apple Calendar on Mac? Connect it here too — Apple requires calendar
   > access to be granted separately on each device."
3. **Per-calendar picker for Apple Calendar.** Mac has one; iOS does not and imports
   *everything*. Port the Mac pattern:
   - Mac reference: `Atlas/Views/Auth/SettingsView.swift:628-667` (checkbox list),
     `Atlas/Services/EventKitService.swift:22-39` (`AppleCalendarSelection`, UserDefaults key
     `calendar.apple.hiddenCalendarIds`), `:209-214` (`readableCalendars()`), `:123-130`
     (`hiddenCalendarIds:` filter param)
   - iOS today: `MobileEventKitService.swift:35` passes `calendars: nil` — unfiltered.
     `MobileStore+Calendar.swift:44-54` passes no filter.
   - `AtlasMobile/Views/Schedule/AppleCalendarConnectRow.swift` is a bare toggle.
4. **No lying buttons audit.** Drew's rule: a control either runs the real flow or becomes a
   status row ("Connected on Mac — manage there"). iOS cannot add/rename/re-map/reconnect/
   disconnect Google or Canvas accounts — those are Mac-only. Audit every Settings control and
   convert dead ones. Building the manage flows on iOS is explicitly **out of scope**.
5. **Adopt the plural loader.** Mobile reads legacy `loadGoogleConnection` (singular); move to
   `loadGoogleConnections`. Works today, just stale.

**Drew's test:** connect Apple Calendar on iOS, uncheck a noisy calendar (US Holidays) → those
events disappear from the schedule, and no button in Settings does nothing when tapped.

## Phase 4 — Continuous day swipe  *(Drew's original #1)*

Today swiping between days is a page flip — the next day appears already loaded. It should
track the finger and come in off-screen, the way Google Calendar feels.

Needs drag state, velocity handling, rubber-banding at the edges, and mid-swipe cancellation.

⚠️ **It must coexist with the hand-rolled drag-to-schedule `DragGesture`**, which exists
precisely because the native APIs misbehaved (see `CLAUDE.md` macOS gotchas — the same caution
applies on iOS). Do not replace that gesture; make the two compose.

**Where:** `AtlasMobile/Views/Schedule/` — `DayGridView.swift`, `DayTimelineView.swift`, and
whatever owns day paging.

**Drew's test:** swipe slowly → the next day tracks your finger continuously; swipe halfway and
release → snaps back cleanly; then drag an item to schedule it → still works.

## Open questions — need Drew's answer before Phase 1 lands

1. **Multi-day all-day end dates.** Google and ICS treat the end as **exclusive** (a Mon–Wed
   event ends "Thu"); the capture flow treats it as **inclusive**. They disagree today
   (`v1.1-backlog.md` §6). Internally we normalize to one — the user-visible question is:
   capturing "conference Monday to Wednesday" should cover Mon/Tue/Wed. *Assumed yes.*
2. **Timed events during travel.** Under the rule above, a 9am ET class shows at 6am after
   flying to California. Correct, and what Google Calendar does. *Assumed wanted, no
   "school stays in school timezone" special case.*
3. **Existing bad rows.** Only Atlas-native all-day rows are affected (Google/ICS already
   correct, Apple never persisted). Migrate them, or leave them and let edits correct them?
   *Recommended: size it with a prod query first, then a targeted migration.*

**Decided without needing input:**
- **DST.** A recurring 9am class stays 9am across the November change, meaning its underlying
  UTC instant shifts an hour. Standard; recurring events are not fixed instants.
- **No user-timezone column.** The UTC-midnight date encoding removes the need.

## Order and rationale

**1 → 2 → 3 → 4 → 5.**

Timezone bugs first: they are the only items actively lying to users, and Phase 1 touches the
data convention everything else reads. Nothing should move underneath it. ICS second — same
class of bug, independent code. Settings and swipe are self-contained. iPad last: it is the
only phase that adds App Store Connect work (screenshots), so it should not block the fixes.
